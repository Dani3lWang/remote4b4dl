## 4 TG 增益的机制分解（本地从 predictions.json 复算）

| 量 | B3 | B3+GRPO | 读法 |
|---|---|---|---|
| 完全命中 exact | 11.5% | **7.5%** | ↓ 判别性变差 |
| IoU ≥ 0.5 | 35.0% | **31.8%** | ↓ 判别性变差 |
| IoU = 0 | 34.1% | **13.5%** | ↓ 空对空归零，是 mIoU 涨的主来源 |
| 预测区间长度（GT 10.43 帧） | 10.51 | **16.05** | 加宽 53% |
| 预测中心相对 GT 偏移 | −3.86 | **−0.23** | 系统偏早被治好 |
| 中心众数占比 | 24.4% | **48.4%** | 输出坍缩 |
| 中心熵 | 3.51 bit | **2.54 bit** | 与 framepos3ep 同级 |
| 不可解析预测 | 3 / 2783 | 2 / 2783 | — |

结论：+0.0321 来自"去偏 + 加宽"的覆盖式打法，不是定位精度提升。纯 IoU 奖励对"加宽换覆盖"是正激励，下一轮须在奖励里加长度/精度约束项（exact 或 IoU≥0.5 门槛奖励、对 pred_len/GT_len 比值的惩罚），否则 mIoU 会继续涨而定位能力不涨。

## 6 日志判读坑（本轮新查，源码 `mllm/vtimellm/rl/grpo_trainer.py`）

1. **`loss` 列几乎不含策略信号**：97% 的步上 `loss ≈ β·kl_mean`（偏差 <5e-4）。每个 rollout 批只做一次内部更新 → `logp_old` 与 actor 同权重、ratio ≡ 1（`:348` 注释自证），组内均值中心化的优势求和≈0，PG 项在记录点上被抵消。把 loss 变小读成"收敛"是错的，学习信号只在 reward / KL 里。
2. **`clip_frac` 与 `ratio_dev` 全程恒为 0**（406/406 步）：不是"裁剪没触发所以健康"，而是单步 on-policy 下结构上不可能非零。这两列无诊断价值。
3. **看单步快照会误判**：step-130 附近的"熵塌缩"（mode_share 0.27 / entropy 2.40）是瞬时谷值，之后 entropy 回升到 2.64、mode_share 回落到 0.189。必须按窗口聚合。

## 7 口径声明（报数必带）

1. 评测使用 `--answer_frames`，属 **oracle 输入选择**；B3 与 GRPO 同口径可比，但非可部署设置。
2. METEOR 主口径为 **NLTK-2005**。B3 原 `metrics.json` 的 0.1747 是 pycocoevalcap jar 口径，与 RL 档的 0.3363 相减会得到假的 +0.1616；GRPO 本轮 jar 交叉校验字段未产出。
3. GPT Score 一列我们全是"—"：B3 / B4a / framepos3ep / GRPO 的 `metrics.json` 无该字段，更早的 B0 / seqv2 / seqv3 落盘值恒为 `0.0`（评测器从未真正调用 GPT API），论文该列无法对齐。
4. 显著性阈值沿用本项目实测 ΔmIoU > 0.013。
5. 评测日志中 3 组 `AttributeError: '_DrainedMeteor' object has no attribute 'lock'` 是 pycocoevalcap `meteor.py:78` 的 `__del__` 清理路径缺陷，非故障；本轮无 `Skipped N items`，30,145 条全部计分。

## 8 下一步

- 奖励侧：在 IoU 之外加长度/精度约束项，目标是把 exact 与 IoU≥0.5 拉回 B3 之上，同时保住 mIoU 增益。
- 探索侧：`center_std` 腰斩意味着第二轮 RL 若仍从 B3 起步，需考虑组大小 G=16（M1 审计对 TG 的建议）或温度/多样性约束，否则覆盖式打法会继续被奖励偏爱。
- 未触达病灶：高帧段（GT start ≥ 25，n=413）在 B4a 过采样、A.2 帧嵌入、GRPO 纯 IoU 三条路线上均未改善（GRPO 仅 +0.0089），仍是首要未解问题。
