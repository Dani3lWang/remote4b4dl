# B4DL GRPO 当前实施方案

> 本文只描述 `rf-grpo` 分支当前可运行实现。早期可行性、三进程草案和已淘汰实验对照已从仓库移除。

## 目标与边界

第一阶段只优化 `time_grounding`。训练基底固定为当前 B3 checkpoint，RL 数据只来自训练集，奖励直接调用 `evaluation.evaluate_model` 的闭区间 IoU 解析。测试集只用于最终验收，不进入训练或调参。

历史 M2/M3 门控使用的是旧 3-epoch B3 checkpoint；改用当前 2-epoch B3 后必须重新运行所有门控。

## 当前结构

| 文件 | 职责 |
|---|---|
| `build_rl_data.py` | 从 B3 训练数据构建 RL JSONL |
| `data.py` | 按视觉帧数分桶和组装 prompt batch |
| `rollout.py` | 分块批量采样 |
| `logprob.py` | 统一计算 old/ref/actor log-probability |
| `reward.py` | 复用官方评测函数计算奖励 |
| `model_utils.py` | 合并 B3、挂载 RL-LoRA、生成侧补丁 |
| `grpo_trainer.py` | 单进程 GRPO 训练与 checkpoint |
| `smoke_m2.py` | 零训练冒烟门 |
| `check_gate.py` | M3 阶段判据 |

## 实现定稿

- 单进程、单卡；RL-LoRA 叠加在已合并 B3 上。
- 参考策略使用同一模型的 `disable_adapter()`，不常驻第二份基础模型。
- old/ref/actor 三路 logp 都走 `forward_sequence`，不使用 generate scores。
- RL-LoRA 使用 fp32 参数和 AdamW 更新；B3 base 冻结。
- rollout 通过 `--gen-max-batch` 分块，避免一次生成 P×G 行造成 KV cache OOM。
- 每次保存只写 RL-LoRA，`save_total_limit=2`。

## 执行顺序

```bash
cd mllm

# 构建训练集
python -m vtimellm.rl.build_rl_data

# M2 通路检查
python -m vtimellm.rl.smoke_m2

# M3 逐级门控
bash scripts/run_grpo_tg.sh m31
bash scripts/run_grpo_tg.sh m32
bash scripts/run_grpo_tg.sh full

# B3 + RL-LoRA 双合并同口径评测
bash scripts/run_grpo_tg.sh eval
```

`run_grpo_tg.sh` 会检查 B3 adapter、RL 数据、M2 `all_pass` 和磁盘余量。正式训练支持 `--resume`。

## 验收

- M3.1：`grad_norm > 0`、`ratio_dev < 1e-3`、`lora_delta > 0`。
- M3.2：跑满 100 步、无 NaN，并人工检查奖励趋势、退化组比例和中心分布。
- Full：完成一个 epoch，checkpoint 与 trainer state 一致。
- Eval：`test_b4dl.py --stage2 B3 --stage3 RL-LoRA` 成功生成完整指标。

对外结果必须同时说明：

1. B3 checkpoint 是 2-epoch 还是历史 3-epoch；
2. 使用 `--answer_frames` 的 oracle 输入选择；
3. 先验地板、格式解析失败率、预测中心熵与众数占比；
4. B3 与 RL 使用完全相同的测试集、生成参数和指标后端。

## 硬约束

- 不复制或改写奖励解析逻辑。
- 不读取测试集来构建 RL 数据、选择 checkpoint 或调整超参。
- 不混用不同 B3 checkpoint 生成的 old logp。
- 任何基底、精度或生成参数变化都必须重跑 M2/M3 门控。
