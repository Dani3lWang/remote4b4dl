## 0. 结论摘要（先看这段）

1. **奖励可用，且与论文指标逐位同源**：审计脚本直接调 `evaluate_model` 的方法重算，TG/existence/binary_qa 三项与 `metrics.json` 的差 ≤ 2.05e-15（S0 PASS）。RL 优化的就是被报告的那个数，不存在"奖励-指标漂移"。
2. **奖励形状定稿：原始 IoU / 0-1 精确匹配，不减地板、不做裁剪**。GRPO 的优势按组内均值中心化，任何**加性**常数在优势里自动抵消（减地板是 no-op）；而"裁到地板以上"是非线性的，实测把组内 std 压掉 35~60%（S4 最后两列）→ 明确禁止。
3. **TG 有可用梯度信号**：G=8 时组内奖励零方差（退化组）比例 TG 6.9% / existence 21.2% / binary_qa 0.5%，E[std r] 分别 0.214 / 0.355 / 0.463。G=16 时 TG 退化组降到 2.4%。
4. **但"躺着答先验常数"在半数样本上并不吃亏**：训练集先验挑出的常数区间 `from frame 005 to frame 026` 在测试集上 **48.7% 的样本比 B3 自己的答案更好、11.6% 打平**（framepos3ep 是 52.5% / 12.8%）。这是 SFT 交叉熵修不动 TG 的量化解释，也是 RL 必须盯住的 hacking 面。
5. **RL 起点取 B3 不取 framepos3ep**：两者 ρ(预测中心, GT 中心) 几乎相同（0.440 / 0.448），framepos3ep 丢的是散布（预测中心 std 7.43→4.46、众数占比 24.4%→49.4%、中心熵 3.50→2.46 bit）。rollout 越贴近众数，组内方差越小（S4 "含常数答案(50%)" 行：TG 的 E[std r] 0.214→0.157）。
6. **新增前置工作**：训练 JSON 只有 `time_grounding` 条目带 `task` 字段（13,124/148,271），其余 135,147 条无任务标签 → 分任务奖励路由与分任务先验地板都缺依据。**M2 第一步就是给 RL 数据补 `task` 标签**。
7. **泄漏红线已验证**：测试集 150 个 `scene_token` 与训练集 699 个交集为 0，按 scene 划分成立；训练侧 `vtimellm/train/dataset.py` 不读 GT 帧号，`--answer_frames` 只存在于评测/注入脚本。

**下一步只做 M2**（rollout 通路冒烟，需占卡但只需分钟级），M3 之前不写 trainer。

## 2. 目标与非目标

**目标**：在冻结评测口径下把 TG 的 mIoU 从 B3 的 0.3467 推到 **≥0.360**（Δ>+0.013 的显著阈值），且 existence/binary_qa 不显著回退（各自 Δ ≥ −0.013），复杂任务生成指标不回退。

**非目标**：不动评测代码与口径；不引入 reward model / GPT judge；第一批不碰 description / temporal_understanding / comprehensive_reasoning；不追求超过论文 Table 3 的生成指标。

**必须随结果一起报告的三个数**（否则无法判断是不是在刷先验）：先验地板 ≈**0.300**（两条训练集常数区间实测 0.2998 / 0.3008，见 §1.4）、黑客面"常数赢"占比、预测中心熵与众数占比（`tg_decode_probe.py` 直接给）。

## 3. 奖励规格（定稿）

| 任务 | 奖励 | 实现 | 备注 |
|---|---|---|---|
| time_grounding | `r = IoU(pred, gt)`，闭区间整数帧 | `EV.compute_miou([EV.extract_time_grounding_frames(p)], [EV.extract_time_grounding_frames(g)])` | 解析失败自然为 0，不另加格式罚 |
| existence / binary_qa | `r = 1[normalize(p) == normalize(g)]` | `EV.compute_accuracy([p], [g])` | 不做长度罚；existence 的目标名子集按同一条规则即可 |
| 复杂任务 | 第一批不进 RL | — | 需要 judge/参考式指标，方差与成本都不合算 |

禁止项：**减先验地板**（对优势是 no-op）、**裁剪到地板以上**（压组内方差）、**阈值化 IoU**（如 `1[IoU>0.5]`，会把 97 个取值压成 2 个、退化组暴涨）、**改 `extract_time_grounding_frames` 以容忍顺序颠倒**（与评测口径分叉）。

KL：`β` 起手 **0.04**（区间 0.02–0.1），per-token k3 估计；采样温度起手 **0.9**（区间 0.7–1.1），按 §1.5 的退化组率调。

优势：组内 `A_i = (r_i − mean_G) / (std_G + 1e-6)`；多任务混批时**按任务分别归一化**（TG 的 IoU 量级与 0/1 匹配奖励混在一起会互压）。可选开关：不除 std（Dr.GRPO 式，避免长度/难度偏置）——M3 做 A/B。

### 4.5 代码级审查结论（2026-09-13，写 trainer 之前）

逐行核对 §4 的"直接复用"假设后，有 8 处会**静默**产出错数（不报错、只是偏），已全部落进 `mllm/vtimellm/rl/`：

| # | 发现 | 证据 | 处理 |
|---|---|---|---|
| 1 | **右 padding 会让批量生成整体错位** | `builder.py` 从不设 `padding_side`；`train.py:343` 设的是 `"right"`；融合层按 `config.tokenizer_padding_side` 重新补位（`vtimellm_arch.py:244`，默认 `'right'`）。右补时 `generate` 读 `logits[:, -1]` 取到的是 pad 位而非最后一个真 token | `model_utils.prepare_for_generation` 同时设 `tokenizer.padding_side='left'` 与 `model.config.tokenizer_padding_side='left'` |
| 2 | **同一 generate batch 内视觉 token 数必须相等**（是正确性要求，不是优化） | `vtimellm_arch.py:89-94`：每个解码步把 attention_mask 补 1 补到 `cache_len+1`，补的个数 = `N`。只有当各行 `N` 相同，前导零个数 `L_in−L_pb` 才等于展开后应有的 `E_max−E_b`，第 94 行 `position_ids = mask.sum(1)−1` 才对。`N` 不同时短行拿到错 mask + 错 position_ids，**不报错**，从污染状态继续生成 | `data.iter_prompt_batches` 按 `n_visual` 分桶；`rollout.generate_batch` 入口硬校验，不等就 `ValueError`。实测只有 8 个不同 `N`（3..10，N=5 占 61%），分桶代价极低。G2.3b 是这条的**反向对照** |
| 3 | **fp16/bf16 混用会给重要性比加系统性偏置** | `builder.py:23` 原写死 `torch.float16`，而 B3 是 `--bf16 True` 训的；`ratio = exp(logp_actor − logp_old)` 跨精度就带了常数偏移，量到的不是策略移动 | `builder.load_pretrained_model` 改成读 `args.torch_dtype`（不传仍是 fp16，**所有既有调用方逐位不变**）；三个 RL 进程统一 bf16。G2.6 在**训练集** prompt 上量 bf16 vs fp16 贪心一致率（不碰测试集） |
| 4 | **温度必须两侧都除** | transformers 在写入 `outputs.scores` 之前已跑完 logit processor，`top_p=1.0` 时 scores 就是 `logits/T` | `rollout` 直接 `log_softmax(scores)`；`logprob.forward_sequence` 除以同一个 `T`。G2.4a 在 T=0.9 下对拍 |
| 5 | **展开布局的 gather 下标要按行算** | 融合层把 1 个 `<video>`(-200) 换成 N 个视觉 embedding 并按**展开后**最长行重补，返回的 logits 与传入的 `input_ids` 不同长 | `E_b = len(prompt_b) − 1 + N_b + len(completion_b)`；左补下 completion 第 j 个 token 落在 `E_max − L_b^c + j`，预测它的 logits 在左一格。每次调用断言 `logits.shape[1] == max(E_b)`，并由途径 C 独立验证 |
| 6 | **RL-LoRA 的 dropout 必须是 0** | B3 的 adapter 是 `lora_dropout=0.05`（`train.py:384-392`）；带 dropout 的 actor 让 `logp_actor` 在前向与重算之间不可复现 | `model_utils.attach_rl_lora(dropout=0.0)`，target_modules 与 B3 的 `adapter_config.json` 一致 |
| 7 | **metatoken 行在 RL 阶段保持冻结** | `train.py:399-409` 的梯度掩码 hook + `weight_decay=0` 是为了让 `<4DLiDAR>/<meta>` 两行可学且不衰减；B3 训好的行已在 merge 后的权重里 | RL 不再挂 hook，`weight_decay` 的这条约束随之不适用（仍沿用 0，与 stage2 一致） |
| 8 | **`pad_token` 只在 `train.py:346` 设过** | 推理路径没人设；且 `KeywordsStoppingCriteria` 在 `inference.py:43` 构造后从未传进 `generate`，是死代码，停止只靠 EOS/max_new_tokens | `prepare_for_generation` 设 `pad_token = unk_token`（id 0，与 train 同）；EOS 是 id 2。`rollout.completion_mask` 按**首个 EOS**（含）截断，不用 `!= pad_id`——否则会误伤合法采样出的 `<unk>` |

**顺带核实的一个 checkpoint 事实**（不是缺陷，但容易被人误判）：B3 的 `non_lora_trainables.bin` 里**只有** `base_model.model.model.embed_tokens.weight (32002, 4096) bf16`。这与代码一致——`train.py:414` 只解冻 `embed_tokens`，`lm_head` 全程不可训；`mm_projector` 被 `get_peft_model` 冻结、由 `initialize_vision_modules` 从 stage1 的 `mm_projector.bin` 单独加载，本来就不该出现在这个文件里。推论：`builder.py:86-87` 给 `<4DLiDAR>/<meta>` 两个**输出**行做的均值初始化，在 `load_lora` 之后不会被任何训练值覆盖，评测出来的 B3（acc 0.7526 / mIoU 0.3467）用的就是均值初始化的 lm_head 元 token 行——**这是设计如此，不是丢权重**。RL 走同一条 `builder` 装配路径，两侧逐位一致，因此不影响本次训练；记下来是为了避免以后有人假定输出侧元 token 学过东西。

## 5. GRPO 单轮迭代的实施流程（逐步枚举）

记 P = 每步 prompt 数，G = 每 prompt 的 rollout 数，L_c = completion token 数。

1. **取样**：从 RL 数据（训练集，含 `feat_range/feat_indices/task/gt`）取 P 条，**按 `scene_token` 分组**（148k/699 ≈ 212 条/scene），组内共享一次 `.npy` 加载与特征张量。
2. **构造输入**：`build_query(human_value, ego_meta, frame_motion, ...)` → prompt 字符串；`tokenizer_image_token(prompt, ...)` → `input_ids (1,L_p)`；`resolve_feat_slice` + `load_features` → `features (N,768)`；`frame_indices` 取条目自带的 `feat_indices`。**不使用 `--answer_frames`**（那是评测侧的 oracle 归因，RL 数据自带真实帧归属）。
3. **rollout（进程 1，无 ZeRO）**：加载 base + SFT-LoRA + RL-LoRA 全 merge 的 bf16 模型（~14GB），`generate(do_sample=True, temperature=0.9, top_p=1.0, max_new_tokens=64, output_scores=True, return_dict_in_generate=True, use_cache=True)`，G 次（或批量 G，见 §6 M2 的对拍门）。
4. **取 actor_old logp（途径 A）**：`outputs.scores` 是每步 `(B,V)` logits → `log_softmax` 后 gather 实际采样 token → `logp_old (G,L_c)`；同时记 `completion_ids (G,L_c)`、`prompt_len`、EOS 位置、`finish_reason`。
5. **算奖励**：decode 出文本 → §3 的奖励函数 → `r (G,)`。**与评测同一份代码**（S0 已证逐位一致）。
6. **组内归一化**：`A = (r − r.mean()) / (r.std() + 1e-6)`；若 `r.std() == 0` → 该组整条丢弃并计数（`degenerate_groups`，对照 §1.5 的 6.9%/21.2%/0.5%）。多任务混批时按 task 分组分别归一化。
7. **ref logp（进程 2，无 ZeRO）**：加载**冻结的 SFT 起点**合并权重（B3），对 `(prompt + completion)` 一次前向，途径 B gather → `logp_ref (G,L_c)`；落盘。ref 权重全程不更新。
8. **落盘交接**：`rollout_{step}.jsonl` = {scene_token, task, prompt_ids, completion_ids, logp_old, logp_ref, r, A}。三段式靠文件交接，任一进程崩了可从这一步续（沿用仓库既有的断点文化）。
9. **训练前向（进程 3，ZeRO-3 + CPU offload）**：base + 冻结 SFT-LoRA + 可训练 RL-LoRA；对同一 `(prompt+completion)` 前向，途径 B 得 `logp_actor (G,L_c)`；prompt 段与 padding 段用 mask 排除（视觉占位 -200 的位置天然被融合层掩掉，completion 段不受影响）。
10. **重要性比**：`ratio = exp(logp_actor − logp_old)`，逐 token。
11. **策略损失**：`L_pg = −mean_over_tokens(min(ratio·A, clip(ratio, 1−ε, 1+ε)·A))`，ε=0.2；聚合方式=先序列内 token 平均、再 batch 平均（短答案下与全 token 平均差异可忽略，但要固定一种并写进配置）。
12. **KL 项**：`kl_t = exp(logp_ref − logp_actor) − (logp_ref − logp_actor) − 1`（k3，非负无偏）；`L = L_pg + β·mean(kl_t)`，β=0.04。
13. **更新**：`backward` → `clip_grad_norm_(1.0)` → AdamW（`weight_decay=0`，与 stage2 一致，否则冻结的 metatoken 行会被衰减）→ 只更新 RL-LoRA 参数（+ 若沿用 stage3 的掩码 hook，则 metatoken 两行）。学习率起手 1e-5（比 SFT 的 1e-4 低一个量级），cosine，warmup 3%。
14. **记录与存档**：每步写 `training_logs/grpo_tg_{ts}.jsonl`：`mean r / std r / 退化组率 / 解析失败率 / 预测中心 std / 众数占比 / 中心熵 / KL 均值 / ratio 被 clip 的 token 占比 / grad_norm`。每 `save_steps` 存 RL-LoRA（`save_total_limit=2`，磁盘只有 18G、单档 4.1G，沿用 framepos3ep 的教训：**存档后立刻删被取代的旧档**）。

**一轮完整训练的规模建议**：P=32、G=8 → 256 条 rollout/步；TG 训练条目 13,124 → 一个 epoch ≈ 410 步。先跑 1 个 epoch（~410 步）看趋势，不要一上手跑 3 epoch。

## 8. 失败模式与止损线

| 失败模式 | 早期信号 | 处置 |
|---|---|---|
| 往先验众数坍缩（重演 framepos3ep） | 众数占比 >24.4% 且上升、中心熵 <3.50 bit、黑客面"常数赢"上升 | 升 β、升 T、检查是否误加地板裁剪；仍坍缩则停，改 RFT/DPO 平价路线 |
| 奖励 hacking（输出超长区间刷 IoU） | 预测长度均值 >12 帧（GT 均值 10.4）而 mIoU 不涨 | §1.2 已示"越界超长"仅 0.09，风险低；真出现则加长度上限硬约束 |
| 组内无信号 | 退化组率 >30% 持续 | 加 G 到 16、升 T；existence 若始终 >30% 则第一批只留 TG + binary_qa |
| logp/口径错 | M2.4 对拍不过，或训练中 KL 突变、ratio 被 clip 的 token 占比 >20% | 停，回到 M2.4；不要靠调 β 掩盖 |
| 吞吐不可行 | M2.5 batch=8 <40 items/s 且 1 epoch >20 h | 缩 P 与 epoch 数，或只做 TG 的 3k 条子集先验证方向 |
| 磁盘写爆 | 余量 <8G | 沿用链式脚本的 `avail_gb` 等待逻辑，不硬写 |
| 贪心-采样错配 | 采样策略奖励涨、冻结口径（贪心）评测不涨 | 以贪心评测为准；必要时降 T 重训，不用采样分数报成果 |

**总止损**：M3.3 一个 epoch 后 mIoU 仍 ≤0.3467，或 M3.2 出现坍缩信号且调参无效 → 停止 GRPO，转 RFT/DPO（训练集采样、测试集 predictions 禁入训练），并把负结果按既有格式归档。

## 9. 红线（延续既有约定）

1. 评测口径冻结：`--whole_scene --per_sequence --answer_frames`，HF offline，六任务全量；`--answer_frames` 的 GT 归因是既有 oracle 约定，**任何报告都要声明**。
2. RL 训练数据只来自训练集；测试集 `predictions.json` 与其 GT **禁入**训练与调参。
3. 调参只看训练集指标；测试集只在 M3.3 / M4.2 两个验收点各跑一次。
4. 奖励只调 `evaluate_model` 的现成函数，不复制、不改写实现。
5. 服务器共用：写操作只在 `/root/autodl-tmp/mmb4dl` 内。
