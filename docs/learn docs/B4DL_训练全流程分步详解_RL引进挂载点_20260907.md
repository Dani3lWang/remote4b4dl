# B4DL 训练全流程分步详解（RL 引进拆解底稿）

> 生成日期：2026-09-07 ｜ 用途：把 mmb4dl 现行 SFT 训练管线拆成**可逐段替换/插入**的步骤，
> 为引入强化学习（RL/RLVR）提供操作底稿。每步给出：命令、输入→输出、产物路径、
> 关键参数、耗时量级、幂等语义，并标注与 RL 的关系（`【RL-锚点】`）。
> 配套阅读：`B4DL_训练代码全景解析_20260907.md`（代码级解读）、`B4DL_复现方案.md`。
> 文内数字截至 2026-09-07；B4a 训练当时正在运行（step ~2392/3519，epoch 2.04）。

---

## 0. 十秒总览：全流程只有 6 个可执行阶段

```
[A] 数据与特征准备（离线、低频）      → b4dl_dataset/*.json + *.npy
[B] Stage1 投影器对齐训练（~2-4h）    → mm_projector.bin
[C] Stage2 LoRA 主训练（~24-35h）     → adapter_model.safetensors + non_lora_trainables.bin
[D] 评测（~3-5h/次）                  → predictions.json + metrics.json
[E] 备份归档（可选）
[RL] 建议插入位置 = C 之后、D 之前（以 B3/B4a 产物为初始化，见 §7）
```

依赖关系（DAG）：**A 是 B/C/D 的共同前提；B 的产物是 C 的输入；C 的产物是 D 的输入；
RL 若在 C 后插入，则复用 A 的数据产物、B 的投影器、C 的权重初始化，产出物仍进 D 评测**。

## 1. 阶段 A：数据与特征准备（一次性/低频，RL 全量复用）

### A1. LiDAR 特征提取（编码器定稿后全量重提，不可增量混提）

Stage2 主训练用整场景特征（850 scenes），Stage1 投影器对齐用单帧特征（28,130 帧，
train 700 scenes 关键帧）。两套都由 LiDAR-CLIP 编码器前向得到（768 维 fp16）。

```bash
# Stage1 特征（sample_token 键控，162K 方案，现役）：
cd encoders/lidarclip
conda run -n wqlc python extract_pc_features_sample_token.py \
    --checkpoint ./lidarclip/checkpoint/vit_l_14.ckpt \
    --scene-metadata /root/autodl-tmp/wql/mmb4dl/dataset/nuScenes-B4DL/metadata/scene_metadata.json \
    --sample-json /root/autodl-tmp/Datasets/nuScenes/v1.0-trainval/sample.json \
    --data-path /root/autodl-tmp/Datasets/nuScenes \
    --save-dir ./b4dl/stage1_features_sample
# → encoders/lidarclip/b4dl/stage1_features_sample/{sample_token}.npy  共 28,130 个 (1,768)

# Stage2 特征（整场景拼接，frame 顺序 = 场景时间序）：
conda run -n wqlc python extract_pc_features.py \
    --checkpoint /path/to/lidarclip.ckpt \
    --scene-json-path ./annotations/scene_metadata.json \
    --frame-json-path ./annotations/sequence_metadata.json \
    --data-path /root/autodl-tmp/Datasets/nuScenes \
    --stage1-save-dir ./b4dl/stage1_features/ \
    --stage2-save-dir ./b4dl/stage2_features/
# → encoders/lidarclip/b4dl/stage2_features/{scene_id}.npy  850 个 (N_frames,768)
```

要点：
- 特征文件名必须与数据 JSON 的键严格一致（`dataset.py` 按 `{feat_folder}/{scene_id}.npy`
  加载并有**启动预检 fail-fast**）；键控方案换代（frame_id → sample_token）后旧特征
  目录退役保留、不得混提；
- 编码器 ckpt 为 PyTorch Lightning 格式：加载需 `weights_only=False` + `strict=False`，
  提取时 lidar_encoder 处于特定模式（与 `val_mse_probe.py` 的 train 模式约定一致）。

`【RL-锚点】` 特征与编码器**冻结不动**：RL 阶段视觉侧完全复用 `stage2_features/`。
RL rollout 的特征加载函数现成：`evaluation/test_b4dl.py:367 load_features()`。

### A5. Metatoken 注入（训练数据最终形态，B3/B4a 口径）

```bash
# B3 口径（meta2 = relative-to-previous 渲染；--answer_frames 仅对 TG 生效）
python scripts/inject_metatoken.py \
    --input ./b4dl_dataset/stage2_full_train_148k.json \
    --ego_meta ./b4dl_dataset/ego_metadata.json \
    --frame_motion ./b4dl_dataset/ego_frame_motion.json \
    --sequence_metadata ../encoders/lidarclip/annotations/sequence_metadata.json \
    --answer_frames \
    --output ./b4dl_dataset/stage2_full_train_seqv3_meta2_148k.json
```

每条样本最终形态（训练 JSON 内联结构）：

```json
{
  "scene_id": "...", "scene_token": "...",
  "task": "time_grounding",
  "feat_range": [6, 14],
  "feat_indices": [6, 8, 10, 12, 14],
  "conversations": [
    {"from": "human",
     "value": "<4DLiDAR>\n<video>\nWhen do the pedestrians appear?\n<meta> The metadata of the first frame is '...' and the metadata of the last frame is '...'"},
    {"from": "gpt", "value": "from frame 006 to frame 014"}
  ]
}
```

要点：`feat_indices`/`feat_range` 是**由 GT 答案恢复**的序列归属（oracle 型输入构造，
SFT 已如此，报告需声明）；`<meta>` 文本与评测侧 `test_b4dl.py build_query()` 同源
渲染（逐字符一致）。

`【RL-锚点】` 此 JSON 即 RL 的**数据源**：`conversations[0]` 是完整 prompt（含任务
标记与 meta 上下文），`conversations[1]` 是 GT（可验证任务的奖励对照），
`feat_indices`/`whole_scene` 决定视觉输入切片。

## 2. 阶段 B：Stage1 投影器对齐（~2-4h；特征换代才重跑）

```bash
cd mllm
bash scripts/stage1.sh   # deepspeed 单卡 29571，或追加参数覆盖
```

| 项 | 值 | 说明 |
|---|---|---|
| 模型 | vicuna-7b 原版（全冻结） | 只训 `mm_projector`（768→4096 单 Linear） |
| 数据/特征 | `stage1_train.json`（161,629 条）+ `stage1_features_sample/` | 每帧一条描述 |
| epochs / lr | 1 / 1e-3 | cosine + 3% warmup |
| batch | 16×8 = 128/step | bf16 + tf32 + grad ckpt |
| 产物 | `checkpoints/vtimellm-vicuna-v1-5-7b-stage1/mm_projector.bin` | 每 200 步存 checkpoint-N/mm_projector.bin |

迭代注意：B0 用 95K-caption 重训版、B1 起用 **162K 重训版**（同一路径覆盖重训），
换投影器后主训练必须重跑（B1 即为此而生）。

`【RL-锚点】` stage1 产物是 RL 初始化的一部分（`--pretrain_mm_mlp_adapter` 指向它），
RL 阶段**冻结**投影器（与 SFT 的 `--freeze_mm_mlp_adapter True` 语义一致）。

### C1. 启动命令（以 B3 配方为例；B0/B1/B2/B4a 是同一驱动器的变体）

```bash
bash scripts/run_stage2_full_seqv3_mixed_b3.sh    # 幂等：自动断点续训

#   --num_train_epochs 3 --learning_rate 1e-4 --save_steps 200 --save_total_limit 3
#   --lora_enable True --lora_r 64 --lora_alpha 128 --freeze_mm_mlp_adapter True
#   --bf16 True --weight_decay 0. --warmup_ratio 0.03 --lr_scheduler_type cosine

```

### C2. 运行机制逐项（RL 训练器设计时可对照）

| 机制 | 实现 | 位置 |
|---|---|---|
| 训练器 | HF `Trainer` 子类 `VTimeLLMTrainer`（stage2 走父类逻辑） | `vtimellm/train/vtimellm_trainer.py` |
| 分布式 | DeepSpeed ZeRO-3 + 参数/优化器 CPU offload（单卡 5090，28GB 窗口） | `scripts/zero3.json` |
| 梯度累积 | 微批 8 × accum 16 = 128/step（no_sync 已被 monkey-patch 兼容） | `train.py:29-40` |
| 可训参数 | 全部 Linear 的 LoRA 分支（lm_head 除外）+ **`<4DLiDAR>`/`<meta>` 两行 embedding（梯度掩码）** | `train.py:335-397` |
| 数据 | Lazy 加载、特征预检 fail-fast、整场景 or 按 feat_indices 切片 | `dataset.py` |
| 断点 | 每 200 步存 1 份、最多 3 份；重启自动取步数最大且含 `trainer_state.json` 的断点 | `train.py:448-465` |
| 验收判据 | 产物存在 + `trainer_state.json` 的 `epoch >= 2.99`（不信任日志） | `run_b4a_pipeline.sh:33-34` |
| 产物 | `adapter_model.safetensors`（LoRA）+ `non_lora_trainables.bin`（两行 embedding）+ config/tokenizer | `train.py:471-484` |

量级实测（B4a，150,222 条）：总步数 3,519 = 148,271/128≈1,174 步/epoch × 3（过采样
后约 1,173/epoch）；实测步速约 24–36 s/step，全训约 24–35h，每小时约 1.7% 进度。

### C3. 显存门控与自动管线（共享 5090 环境的现实约束）

```bash
bash scripts/run_b4a_pipeline.sh [1|2]
# 阶段1（训练）：nvidia-smi 空闲 >= 28GB → 启动；失败自动断点续训重试 ×3
# 阶段2（评测）：空闲 >= 14GB → 启动；失败重试 ×5（timeout 5h/次）
```

`【RL-锚点】` RL 训练比 SFT 更吃显存与算力（需要采样 + 多次前向），**必须沿用
门控/续训/判据化验收这套外壳**（`run_b4a_pipeline.sh` 的骨架可直接复制成
`run_rl_pipeline.sh`），并预留比 28GB 更高的门控阈值或 offload 策略。


### D2. 评测内部机制（= RL 奖励计算器的现成零件库）

生成：`vtimellm/inference.py:inference()`（逐条、`do_sample=False`、
`temperature=0.05`、`num_beams=1`、`max_new_tokens=1024`、`</s>` 停止符）；预测断点
原子落盘（`test_b4dl.py:_save_checkpoint`，每 50 条）。

打分：`evaluation/evaluate_model.py` 的 `B4DLEvaluator` 一族函数：

| 函数（位置） | 作用 | 任务 | RL 角色 |
|---|---|---|---|
| `normalize_answer` (:323) | 答案归一 | 全部 | 奖励前处理 |
| `compute_accuracy` (:347) | 精确匹配率 | existence / binary | **规则奖励（可验证）** |
| `extract_time_grounding_frames` (:331) | 文本→(start,end)，解析失败记 0 | time_grounding | **奖励解析器（现成）** |
| `compute_miou` (:354) | 区间 IoU | time_grounding | **稠密规则奖励（现成）** |
| `compute_bleu4/metor_nltk_2005/rouge_l/bertscore` | 参考式文本指标 | description 类 | 候选奖励（注意双后端口径） |
| `compute_gpt_score` (:512) | GPT-4o 判官逐条打分 | description 类 | judge 奖励 / 偏好构造 |
| `evaluate_all`/`compute_final_score` (:577/:598) | 汇总结论（acc/mIoU 口径与论文 Table 3 对齐） | 全部 | 每轮 RL 的 checkpoint 评估 |

最终分数定义（论文口径）：`accuracy = mean(existence, binary)`；
`mIoU = time_grounding IoU`；复杂任务看文本指标。显著阈值 ΔmIoU>0.013。

### D3. 评测耗时与代价

- 测试集规模（`test_qa.json`）：30,145 条 = TG 2,783 + binary 7,525 + existence 3,770
  + description 3,770 + temporal 4,757 + comprehensive 7,540（150 scenes）；一次全量
  评测数小时（B4a 管线给 5h timeout）；text 指标中 BERTScore/METEOR-jar 有额外耗时
  与系统依赖（java），规则指标（acc/mIoU）零依赖秒级。

`【RL-锚点】` **评测是离线仪表盘**，每 N 步或每 epoch 对冻结测试集跑一次；RL 训练
**循环内的奖励**不能直接调用整套评测（太慢），应只调用规则函数（见 §7.2）。

## 7. RL 引进挂载点拆解（核心章节）

### 7.1 插入位置与初始化

```
现网:  [A 数据] → [B stage1] → [C SFT-LoRA] → [D 评测]
RL  :  [A 数据] → [B stage1] → [C SFT-LoRA] → [RL 训练] → [D 评测]（同口径）
                                              ↑
                    初始化 = C 产物（B3/B4a adapter+non_lora）+ B 投影器 + vicuna 基座
```

- **推荐初始化**：`-mixed-b3`（或 B4a 完成后）的 `adapter_model.safetensors` +
  `non_lora_trainables.bin`，即当前最优 SFT 策略，RL 在其上继续优化（on-policy
  起点与论文数字可比）；
- **LoRA 挂法二选一**：
  a) 直接在原 adapter 上续训（参数空间连续，靠 KL 约束不过度偏离）；
  b) **merge 后挂新 LoRA**（复用现成 stage3 代码路径：`load_lora → merge_and_unload
  → get_peft_model`，`train.py:352-360`）——RL 只动新分支，旧知识冻结更干净，推荐；
- RL 期间 metatoken 两行 embedding：可继续训（现有梯度掩码 hook 与 LoRA 兼容，
  `train.py:367-397`），也可 `--train_meta_embed False` 冻结——两种都已被代码支持。

### 7.2 六任务 → 奖励信号映射（决定 RL 算法选型）

| 任务 | 输出形态 | 现成判定 | 奖励性质 | RL 建议 |
|---|---|---|---|---|
| existence / binary | 短句（Yes/No 类） | `compute_accuracy`（归一后精确匹配） | 0/1 可验证、较稠密 | **RLVR 首选**：规则奖励，无 reward model |
| time_grounding | "from frame X to frame Y" | `extract_time_grounding_frames` + `compute_miou` | IoU∈[0,1] 稠密可验证、但有解析失败=0 的稀疏陷阱 | **RLVR 首选**：奖励现成且与论文指标同构 |
| description | 长句叙述 | `compute_bleu4/meteor_nltk/rouge_l/bertscore` | 参考式、有虚高/口径坑 | 可作 KL 之外的辅助奖励；**慎用 jar 后端**（进程级不可批量） |
| temporal_understanding / comprehensive | 长句 | 同上 | 同上 | 同上；或走 judge（`compute_gpt_score`） |

关键观察（写进设计）：
- **TG 是 RLVR 的最自然目标**：奖励函数与论文主指标（mIoU）**逐位同构**，不存在
  reward hacking 的度量偏差；解析失败（模型输出非 "from frame…" 格式）直接给 0 的
  语义已被评测代码定义（`evaluate_model.py:331-345` 注释），RL 中可再加格式正则的
  中间 shaping；
- **existence/binary 的 GT 答案需要归一化**（`normalize_answer`）后才能精确匹配，
  SFT 后这些任务 acc 已 0.75+，奖励空间偏饱和，RL 增益可能小，但适合做**管线验证**；
- description 类任务建议从 judge/参考式奖励起步做对照实验，不放进第一个 RL 里程碑。

### 7.3 rollout 侧最小改造点（现状盘点）

现成可直接用的（零改造）：
- prompt 构造：训练 JSON 的 `conversations[0]` 已是完整注入文本；评测侧
  `test_b4dl.py:build_query()` 是等价重建器（含 meta 同源渲染）——两者任选其一
  作为 RL prompt 源；
- 采样入口：`inference()` 已有 `do_sample`/`temperature` 开关（默认关）；RL 只需
  `do_sample=True, temperature≈0.7-1.0` 打开即可产生多样 rollout；
- 特征供给：`load_features()`（场景 .npy → (N,768) fp16 CPU tensor）现成；
- 停止条件：`KeywordsStoppingCriteria`（`</s>`）现成，防止采样跑飞；
- 奖励计算：7.2 表的函数现成（纯规则函数零依赖、可向量化/并行）。

需要新建的（工作量小但必须）：
1. **RL 数据集适配层**：SFT 的 `dataset.py` 输出 (input_ids, labels, images) 且 labels
   掩码答案；RL 需要 (prompt_ids, images, task, gt) 且 **labels=None**（无 teacher
   forcing）。建议新增 `vtimellm/train/rl_dataset.py`（可复用 `LazySupervisedDataset`
   的加载/切片逻辑，去掉 mask、补 task/gt 字段），不污染 SFT 数据路径；
2. **批量 rollout**：现网逐条 batch=1。RL 需要吞吐，可按"帧数分桶 + 同桶 pad 后
   左对齐"做 batch generate——多模态融合已支持变长 list images
   （`vtimellm_arch.py:52-57`），但 `prepare_inputs_for_generation` 的 images 透传
   是单条假设，批量需验证（`model.generate` 传 list 或统一帧数张量两种路线）；
3. **旧策略 logprob（KL 项）**：`model.generate` 不返回 token logprob；GRPO 需对
   采样的 rollout 序列做一次前向（actor 与 ref 各一次）取逐 token logp——
   `transformers 4.31.0` 下可用 `model.forward(input_ids, labels=rollout_ids)` 的
   技巧（labels=rollout 时 loss 即负 logp 之和）或手工 gather；
4. **RL 训练循环**：见 7.4 框架选型。

### 7.4 训练侧工程约束（先读再选框架）

| 约束 | 现状 | 影响 |
|---|---|---|
| 依赖版本锁定 | transformers 4.31.0 / peft 0.4.0（旧式 API）/ deepspeed 0.16.4 / torch 2.5.1 | **新版 TRL（GRPO 需较新 transformers）大概率不兼容**；升级环境会连带 flash-attn/sm_120 问题 → **建议自写最小 GRPO/PPO 循环**（本仓库已有自写 Trainer 与 monkey-patch 先例），或先做兼容性冒烟 |
| 分布式 | ZeRO-3 + CPU offload，单卡 | rollout 与训练同进程可行（on-policy 采样用同一模型）；显存门控阈值需上调或采样时临时 offload 权重 |
| vLLM 加速 | 5090 sm_120 生态未知 | 不依赖 vLLM 的路线最稳：batch 由 HF generate 提供（吞吐低但正确） |
| 参考模型 | 无现成 ref | GRPO 的 KL 参照 = **RL 起点策略**（SFT B3 权重）的冻结副本；同卡双份 7B 权重放不下时，ref 前向可与 actor 共享权重缓存后丢弃（逐 batch 计算） |
| 采样多样性 | 推理默认贪心 | RL 需 `do_sample=True`；低 temperature 与 `no_repeat_ngram` 可作防退化保险 |
| 评测口径 | 冻结在 `--whole_scene --per_sequence --answer_frames` | RL 每轮 checkpoint 用**同一命令**评测，否则不可比 |

### 7.5 Oracle 与泄漏边界（RL 设计红线）

- 训练数据 `feat_indices/feat_range` 由 GT 答案恢复（`--answer_frames`），SFT 已如此
  使用；RL **沿用同一输入构造 = 与 SFT 等价的 oracle 程度**，不新增泄漏，但报告
  必须声明（既有约定）；
- RL 奖励用 GT 计算（可验证任务）= 正常利用标签，无泄漏；
- **禁止**把评测集的任何信息（含 GT 帧号）引入 RL 训练数据的输入构造——现网评测
  侧 `--answer_frames` 的 oracle 只存在于评测进程，RL 数据源是训练 JSON，天然隔离，
  保持即可；
- whole_scene 配方（B3+）下输入不含任何序列归属，是 RL 最干净的选择（推荐 RL
  继续用 `--whole_scene` 输入，奖励里再学帧号）。

### 7.6 建议里程碑（每个都有可判定的验收）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 奖励离线审计（~1 天，零 GPU） | 用 B3 权重在训练集子集上采样（贪心即可），统计：各任务 parse 成功率、奖励分布、与 SFT loss 的关系；确认 TG/existence 奖励函数与评测数值一致（抽查 100 条对拍 `metrics.json`） | 对拍一致；得到奖励基线与稀疏度报告 |
| M2 rollout 通路冒烟（~1 天） | 新建 rl_dataset + batch rollout + 奖励计算，100 条样本跑通"采样→打分→logp"闭环 | 奖励分布合理、无 NaN、显存达标 |
| M3 单任务 RL 对照（~2-4 天） | 自写最小 GRPO，先在 **existence**（或 TG 子集）上训，与 SFT 起点同口径评测 | acc/mIoU 不降或提升；KL 不炸；复现 SFT 基线可 |
| M4 多任务扩展（~1-2 周） | TG + binary 混合 RLVR；description 类引入 judge/参考奖励做消融；每 epoch 冻结口径评测存档 | 论文表 3 全任务对照表 + 消融（奖励类型/系数/温度） |

M1 建议最先做：它会把"奖励函数与评测同构"从假设变成断言，且成本最低。
