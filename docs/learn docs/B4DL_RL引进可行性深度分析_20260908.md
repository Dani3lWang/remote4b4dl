三个结论：

1. **CLAUDE.md 的依赖清单已过期**（应为 2026-08 的 sm_120 SDPA 修复连带升级所致，
   transformers>=4.45 才能用原生 SDPA）——RL 设计以实测 4.47.0 为准。本分析完成后
   同步修正 CLAUDE.md。
2. **TRL 装得上**：`pip index` 可达 PyPI；TRL 0.15.2 与 0.17.0 的 METADATA 实测均为
   `Requires-Dist: transformers>=4.46.0`，与现环境 4.47.0 不冲突。装 TRL **不需要**
   升级 transformers（升级会连带打破 B4a 已验证的训练栈，风险高）。
3. **TRL 用起来仍需改造**：GRPOTrainer 走 `logits_to_keep` 前向取逐 token logp，

   不是 TRL 原生 VLM 格式。集成 = 自定义 model 包装器 + 自定义 data collator，
   改造量与"自写最小 GRPO"（约 300 行，复用仓库现有组件）相当。**结论：自写最小
   GRPO 优先**（仓库文化即自写 Trainer/monkey-patch 先例），TRL 留作后续对照实验。

## 2. 奖励语义逐任务精确目录（RL 奖励将直接继承）

### 2.1 existence / binary_qa → `compute_accuracy`（0/1 精确匹配）

`evaluation/evaluate_model.py:323-352`：

```python
@staticmethod
def normalize_answer(answer: str) -> str:
    answer = answer.strip().lower()
    answer = re.sub(r'^(the answer is|answer:|a:)\s*', '', answer)
    answer = re.sub(r'[^\w\s]', '', answer)
    return answer.strip()

def compute_accuracy(self, predictions, ground_truths):
    correct = sum(1 for p, g in zip(predictions, ground_truths)
                  if self.normalize_answer(p) == self.normalize_answer(g))
    return correct / len(predictions)
```

RL 语义要点：

- 奖励 = 归一化后**整串精确相等**；前缀剥离只认 `the answer is / answer: / a:` 三种；
- 实测 GT 形态（见 §3）：existence 答案 = `yes/no` 或短对象名（`car/truck/pedestrian`…），
  binary 几乎纯 `yes/no`——所以"归一化精确匹配"对这两个任务是**正确且唯一的**奖励源，
  无需 judge；
- 陷阱：模型输出带句号/大小写/前缀都不影响（被归一化掉），但输出成句（"Yes, there
  is a car"）会得 0。SFT 后的模型已学会短答格式，RL 不会遇到大面积的格式稀疏问题。

### 2.2 time_grounding → `extract_time_grounding_frames` + `compute_miou`（IoU ∈ [0,1]）

`evaluate_model.py:331-377` 节选：

```python
@staticmethod
def extract_time_grounding_frames(text):
    for pat in (r'from\s+frame\s+(\d+)\s+to\s+frame\s+(\d+)',
                r'frame\s+(\d+)\s+(?:to|-|and)\s+frame\s+(\d+)',
                r'from\s+frame\s+(\d+)\s+until\s+frame\s+(\d+)'):
        m = re.search(pat, text.lower())
        if m:
            return {'start_frame': int(m.group(1)), 'end_frame': int(m.group(2))}
    return None   # 无区间 → IoU 记 0，绝不记 frame 0

def compute_miou(self, predictions, ground_truths):
    ...
    inter = min(pe, ge) - max(ps, gs) + 1          # 闭区间，含端点
    union = (pe - ps + 1) + (ge - gs + 1) - inter
    ious.append(inter / union if union > 0 else 0.0)
```

RL 语义要点（这是**全仓库最适合 RLVR 的奖励**）：

- 奖励与论文主指标 mIoU **逐位同构**（评测的每条样本贡献就是这条的 IoU），不存在
  reward hacking 的度量偏差；
- 奖励是稠密实数（区间重叠多少拿多少），不是 0/1——GRPO 的组内优势天然可用；
- 两种失败模式分开对待：**格式失败**（无区间 → 0，硬惩罚）与**定位失败**（有区间
  但 IoU 低，软惩罚）。可在 RL 训练中额外给格式加 shaping（见 §7.3），评测侧不动；
- 解析只认三种英文句式，训练时若模型出现其它合法变体（"from 6 to 14"）会漏判——
  可用奖励模块的**同样解析器**做 RL 奖励，保证"训练奖励与评测判定同码"（防止
  训练奖励认、评测不认的度量漂移）。

### 2.3 复杂任务（description / temporal / comprehensive）→ 参考式 + judge

`evaluate_task` 路由（`evaluate_model.py:552-572`）：existence/binary → accuracy；
TG → miou；COMPLEX_TASKS → bleu4 + meteor（双后端）+ rouge_l + bertscore +
（可选）GPT-4o 0-100 judge。RL 含义：

- BLEU/ROUGE/METEOR 均可离线算（METEOR 用 NLTK-2005 主口径），但都是**参考式**、
  逐条不稳定，作为 RL 奖励有已知的虚高/稀疏问题；
- BERTScore 需要 roberta-large 前向（GPU OOM 时自动 CPU 回退，慢）；
- GPT-4o judge 有调用成本与延迟，且逐条方差大；**建议复杂任务不进第一个 RL 里程碑**。

### 2.4 聚合口径（RL checkpoint 评估沿用）

`compute_final_score`：accuracy = mean(existence, binary)；miou = TG 均值；复杂任务
按指标跨任务平均。**RL 每轮 checkpoint 用 §冻结口径的命令（--whole_scene
--per_sequence --answer_frames）离线评测**，与 B3/B4a 数字直接可比。

## 4. Rollout 通路分析

### 4.1 现状（test_b4dl 主循环，`test_b4dl.py:549-639`）

- 逐条 batch=1：`load_features(scene_id).cuda()`（按 scene 缓存）→
  `build_query()`（注入 `<4DLiDAR>/<video>/<meta>`，与训练注入同源）→
  `inference()`（`inference.py:36-74`）；
- 生成参数：`do_sample=False, temperature=0.05, num_beams=1, max_new_tokens=1024`，
  停止符 `</s>`（`KeywordsStoppingCriteria`）——RL 需要改成 `do_sample=True,
  temperature≈0.7-1.0`，其余参数（停止符、max_new_tokens）可沿用；
- 特征缓存 per scene 是现成优化：**同一 scene 有约 212 条 QA**（148k / 699 scenes），
  rollout 按 scene 分组可把 .npy 加载与 prompt 构造摊薄。

### 4.2 批量化改造点（M2 的第一个实验）

- 按 scene 分组后同 scene 内 batch：整场景输入的特征张量逐条相同，`model.generate`
  的 `images` 可传 **list（每样本 (N,768)）**——融合层 `vtimellm_arch.py:52-57` 已
  支持 list cat+split；但 `prepare_inputs_for_generation` 的逐步 images 透传只验证过
  batch=1，**批量 + cache 的正确性需实测**（M2 用贪心对拍：batch 结果必须与 batch=1
  逐位一致）；
- 帧数分桶：4 个桶（39/40/41/32），桶内 pad 到同长；
- 预期收益：batch=8-16 时短答案任务吞吐 ×4-8，单轮 rollout（如 6k prompts × 4
  samples）从 ~7h 降到 ~1-2h。

### 4.3 采样多样性保险

- `temperature=0.7-1.0` + `do_sample=True`；`no_repeat_ngram_size=3` 可防复读崩溃；
- GRPO 组内对比需要每组 4-8 条采样；TG 短答案的组内多样性低是**天然风险**（格式
  高度受限），温度过高会大量产出不可解析输出 → 格式失败给 0 的惩罚在 GRPO 里会
  形成强梯度信号，反而有利（这正是 RLVR 对该任务最有价值的地方）。

## 5. Logprob 获取路径（transformers 4.47 实测可用 API）

| 途径 | 机制 | 适用 | 代价/注意 |
|---|---|---|---|
| A. `generate(output_scores=True, return_dict_in_generate=True)` | `outputs.scores` = 每个生成步的 logits | **actor 采样步的逐 token logp**（新 token 才有 score，正好是 RL 要的部分） | logits (B,1,V) 每步；V≈32k，B=8 时每步 512KB，整段 600 token ≈ 300MB 峰值，可接受 |
| B. `forward(logits=...)` 手工 gather | 对完整序列 (prompt+completion) 一次前向取 logits，在 shift 位置 gather 出每 token logp | **ref（旧策略）的逐 token logp**、actor 训练步 logp | 自写 ~10 行；logits (B,L,V) fp16：L=600,B=8 → 307MB，可接受；ref 前向要**第二个权重副本**（见 §6） |
| C. `forward(labels=seq)` 用 loss | loss 是 CE 均值（已 reduce） | 只能做整体校验，不能逐 token | 用于 M2 校验：B 途径的均值 == loss |

实现注意（4.47 + 自定义多模态 forward）：

- ref logp 前向传完整 input_ids（含 `<video>` 占位 -200）+ images，融合层会把视觉
  位置标签掩掉——**completion 部分的 logp 不受影响**，正是所需；
- 训练步 actor logp 在 ZeRO-3 下 forward：lm_head 权重被分区，logits 计算有
  all-reduce，B×L 要控制（M3 用 B=4-8、L≤512 可行）；
- M2 验收：途径 A 的 logp 与途径 B 在相同序列上对拍（差异应 <1e-3），途径 B 均值
  == 途径 C loss（构造 labels=seq）。

## 6. 显存账本与进程/阶段设计

实测 GPU：5090 约 32GB（本会话快照 used 19GB / free 13GB，与 CoRViD 等共存）；
门控沿用：训练 ≥28GB 窗口、评测 ≥14GB 窗口。

| 对象 | 显存 | 说明 |
|---|---|---|
| 合并后推理模型（load_pretrained_model → merge_and_unload，fp16 7B） | ~14GB | 评测/rollout 用，无 ZeRO |
| ZeRO-3 + CPU offload 训练态 | 门控 28GB 窗口内可跑（B4a 已证） | 权重在 CPU，激活+优化器态在 GPU |
| ref 模型第二副本（fp16 7B） | 再 +14GB | **同卡同时放不下**（14+14+激活 > 32GB） |

因此单卡 RL 的**推荐执行形态 = 三段式进程**（契合仓库现有"阶段化 shell + 门控"
文化）：

1. **rollout 进程**：加载合并后的 actor（base+SFT-LoRA+RL-LoRA 均 merge）→ 按 scene
   分组批量采样 → 序列 + 得分落盘（JSONL/parquet）。显存 = 14GB + 生成缓存，14GB
   门控即可；
2. **ref 打分进程**：加载合并后的 **SFT 起点权重**（即 B3/B4a 合并模型）→ 对 rollout
   序列做途径 B 前向 → ref logp 落盘。显存同 14GB；
3. **训练进程**：ZeRO-3 载入 base + SFT-LoRA（冻结）+ RL-LoRA（训练），读序列 +
   ref logp，算 GRPO loss 更新 RL-LoRA。显存 28GB 门控。

替代方案（不用三段式）：ref 前向改 CPU offload 逐段算（慢 ~10-20×，但单进程）——
不推荐，除非 rollout 规模很小。

## 7. 算法与任务选型结论

### 7.1 算法：自写最小 GRPO（对照：TRL 留作 B 方案）

- **GRPO**（组相对优势、无价值网络）是单卡 7B + ZeRO-3 的现实解：不需要额外的
  critic 权重副本；KL 用 ref logp 的 per-token 近似即可；
- 核心组件清单（均可复用/照抄仓库现有代码）：
  `load_pretrained_model`/`load_lora`（模型装配）、`build_query`（prompt）、
  `load_features`（视觉）、`inference()` 改 do_sample（采样）、
  `extract_time_grounding_frames`+`compute_miou` 语义与 `normalize_answer`（奖励）、
  `run_b4a_pipeline.sh` 的门控/续训/判据骨架（调度）；
- 需要新写：rl_dataset（labels=None + task/gt 字段）、批量 rollout、logp gather
  （途径 A/B）、GRPO loss（约 40 行）、checkpoint 评测钩子。

### 7.2 任务选择（第一批 RLVR 范围）

| 任务 | 纳入 | 理由 |
|---|---|---|
| time_grounding | **是（主）** | 奖励≡论文 mIoU；IoU 稠密；训练/测试共 13,124/2,783 条全可解析；B3 残余偏差（−3.9 帧偏早、高帧段欠覆盖）正是 RL 能直接修的 |
| existence + binary_qa | 是（陪跑+验证） | 奖励 0/1 同构、格式简单、生成短；SFT 已 0.75-0.78，期望增益小但能验证管线正确性 |
| 复杂任务三兄弟 | 否（第一批） | 奖励需要 judge/参考式指标，成本与方差都不合算；作为第二批消融 |

多任务混合训练时：**按任务归一化优势**（每任务组内减均值除方差），否则 TG 的
IoU 量级与 0/1 匹配奖励混在一个 batch 会互压。

### 7.3 奖励 shaping 建议（训练侧，评测侧零改动）

1. TG：`r = IoU`；**格式失败给 0**（与评测同码）——不加额外格式罚，避免与评测
   口径漂移；可选 soft shaping：`r += 0.1 * [pred 可解析]` 仅在 M3 收敛困难时启用；
2. 简单任务：`r = 1[normalize(pred)==normalize(gt)]`；不做长度罚（短答案任务输出
   长度天然收敛）；
3. KL 系数起手 0.04-0.1，按 ref-logp 漂移监控调整；温度 0.7 起手。

### 7.4 口径与红线（延续既有约定）

- RL checkpoint 评测 = 冻结命令 `--whole_scene --per_sequence --answer_frames`；
- RL 训练数据 = stage2/stage3 训练 JSON 重新注入 meta2（与 SFT 数据逐字符同源）；
  `--answer_frames` 的 GT 归因属既有 oracle 约定，不新增泄漏，报告继续声明；
- 奖励用 GT 计算 = 正常监督使用，无泄漏；评测集信息（含 GT）不进训练数据。

## 8. 待验证清单（M1/M2 更新版）

**M1 奖励离线审计（零 GPU，~1 天）**——比底稿更省力：B4a 评测跑完后
`eval_results/stage2_full_seqv3_mixed_b4a/predictions.json` 就是现成的
"当前 SFT 策略 × 全测试集"样本：

1. 用 §2 的奖励函数逐条重算 TG（IoU）+ existence/binary（0/1），输出直方图与
   **格式失败率**（SFT 模型当前 TG 不可解析占比、简单任务非短答占比）——这决定
   RLVR 起点的稀疏度；
2. 对拍 100 条：RL 奖励模块的逐条值与 `metrics.json` 的聚合口径一致；
3. 产出"奖励基线报告"（B4a 策略的 TG 平均奖励 = 其 mIoU 0.34xx，简单任务平均
   奖励 = 其 acc）。

**M2 rollout 通路冒烟（~1 天）**：批量 vs 单条贪心对拍（逐位一致）+ 途径 A/B/C
logp 三方对拍 + 显存实测（14GB 门控下 batch 上限）。

**M3 单任务 GRPO（TG，~3-5 天）**：三段式进程、r=IoU、每 epoch 冻结口径评测、
对照 B3/B4a mIoU 0.3467 基线。

**M4 多任务扩展（~1-2 周）**：+existence/binary 混合（按任务归一化优势）、
复杂任务 judge/参考式奖励消融。

---

## 9. 结论摘要

1. **环境比文档新**：transformers 4.47.0 / torch 2.8.0 / peft 0.13.2，现代
   logprob API 全可用；TRL 0.15-0.17 与 4.47 兼容且 PyPI 可达，但集成改造量≈自写
   最小 GRPO，推荐自写；
2. **奖励零成本继承**：TG 的 IoU 奖励与论文主指标逐位同构（训练 13,124 条 100%
   可解析），existence/binary 归一化精确匹配即可——**第一批 RLVR 不需要任何 reward
   model 与 judge**；
3. **数据归属现成**：任务归属用官方 stage2/stage3 文件级分割 + 重新注入 meta2，
   无需启发式路由；
4. **工程形态**：三段式进程（rollout / ref 打分 / ZeRO-3 训练）+ 现有门控/续训
   外壳；rollout 只做短答案任务，按 scene 分组批量可把单轮成本压到 1-2h；
5. **风险清单**：批量 generate 的 images 透传未验证（M2 第一实验）、ZeRO-3 下
   logits 前向的显存上限（B≤8 实测）、GRPO 组内低多样性（温度调参）、
   格式失败稀疏度（M1 先测）。
