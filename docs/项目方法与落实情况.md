## 状态定义

- **已实现**：对应代码路径存在，且其实现范围可从代码和文档确认。此状态不自动代表实验验收通过。
- **实验已完成**：有可追溯的运行记录、退出状态、配置/数据/权重身份和规定范围内的结果。
- **部分实现**：已完成部分模块或原型，仍有明确的数据、流程、指标或集成缺口。
- **待实现**：仓库中尚无所需实现。
- **待验证**：代码或产物已存在，但当前没有足够证据确认正确性、性能或完整验收。

状态必须按具体范围描述。例如“单帧空间原型已实现”不能扩写为“4D 实例分割已完成”；“脚本退出码为 0”也不能代替指标验收。

## 每次代码更新的记录要求

凡修改功能代码、模型、数据处理、训练/评测入口、配置或对外接口，必须在同一变更中更新本文“变更台账”，至少填写：

1. **方法**：采用的算法/数据处理规则，说明关键输入、输出及边界条件；若方法不变，明确写“方法不变”，并说明本次改动落在哪一环节。
2. **实现**：具体改动的模块/文件，以及代码现在实际执行的行为。
3. **落实状态**：已实现、部分实现、待验证或实验已完成，并指出未覆盖的范围。
4. **验证证据**：本次实际执行的检查、测试、训练或评测及其结果；没有执行时写“未执行”，不可推断通过。
5. **追踪信息**：日期、分支，以及提交号；未提交时标注“工作区未提交”。

只改文档、注释、格式或不影响行为的重命名时，可以记录“方法不变”及文档/维护项，不需要虚构测试结果。若一次更新涉及多个独立方法，应拆成多条记录或在同条中逐项说明。修复后须更新原有状态或追加跟进记录，不能让过时的失败/待办状态长期冒充当前状态。

## 变更台账

### 2026-10-30 / upcore：BF16 概率偏差的数值稳定处理

真实 7B 的新版本在第 1 次 GRPO 更新后，第 2 步采样有 token 的概率比超出既定 PPO 裁剪区间，保护生效并停止，正式训练未启动。按第 1 步检查点和随机状态重放第 2 步：默认 BF16 的 16 条候选有 2 个 token 超界，最大 log-prob 差为 0.239；仅使用 FP32 输出头仍有超界。关闭 BF16 降精度累加并使用冻结的 FP32 输出头后，同一重放批次无超界，最大差异为 0.158。

实现：Transformer 保持 BF16、可训练参数保持 FP32；输出投影计算改为冻结 FP32，关闭 BF16 降精度累加，并把这些数值设置加入训练恢复和评测对比身份。严格的逐 token PPO 裁剪保护不变。已补充输出头精度和梯度回归；完整 50 步 GRPO、显存及效果仍需重新验证。

### 2026-10-30 / upcore：真实 GRPO 采样概率核验与修复

RTX 4090 上真实 7B 的 50 步 SFT 工程短跑完成，峰值保留显存约 13,840 MiB；过程 GRPO 在第一步更新前因采样与重算 log-prob 最大差异 0.112 超出旧的 0.1 保护阈值而停止。对同一 SFT 检查点和前四题的 16 条真实候选复核，14 条结构有效；1,143 个 token 中 12 个差异超过 0.1，最大 0.131，均未使未更新策略的概率比超出 0.2 的 PPO 裁剪区间。尝试 BF16 严格累加和 FP32 输出头后仍存在大于 0.1 的个别差异。

修复：保存生成时实际采样分布的 old-policy log-prob；BF16 重算偏差由未更新策略的概率比是否进入 PPO 裁剪区间来保护，超界立即停止，CPU 对齐保持严格容差。该修订明确记录数值偏差，不把采样与整段前向视为完全一致。新版本的完整 GPU 50 步过程短跑、正式训练和效果评测仍需核验。

### 2026-10-30 / upcore：真实 CUDA 预检修复显存统计初始化

在 RTX 4090 云端实例上，完整几何父集和 B3/SST 身份核验通过，v2 推理数据对 83,952 题、34,149 帧的原始标注审计通过。第一次 7B SFT 工程预检在加载模型前退出：PyTorch CUDA 上下文尚未初始化时调用 `reset_peak_memory_stats`，报 `Invalid device argument`，没有产生训练更新。

修复：在重置峰值统计前显式初始化 CUDA，使模型加载过程仍包含在峰值统计范围内；补充初始化顺序和 CUDA 不可用的回归测试。本机 30 项推理测试通过；修复后的真实 GPU 工程预检、完整训练和效果评测仍需分别核验。
